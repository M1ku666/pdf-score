# 提交规范 · PDF Score

用户在聊天框里打出 `commit` 时怎么做。执行脚本：`scripts/agent-commit.mjs`。

两种说法：

| 用户打的字 | 怎么做 |
| --- | --- |
| `commit xxxxx` | `xxxxx` 就是提交消息（**类型前缀由 agent 判定**）→ **直接提交**，不用再找他确认 |
| `commit` | agent 自己拟一条消息 → **先给用户确认**，确认后才提交 |

用户原话：

> 我一般让多个agent一起工作，我希望在我用聊天框打出commit的时候，让这个agent把当前会话里还没有提交过的改动，在让我预览并确认了message之后提交
> 不push。另外你还要注意多个agent会不会有竞争问题
> 以后message只写一行就行了
> 我说commit xxxxx，前缀类型你自己判定，然后把xxxxx定做一行的提交消息直接提交。如果只说commit，那你就生成消息然后给我确认

---

## 1. 提交范围 = 当前会话的改动

- 清单来自**本次会话自己创建 / 修改 / 删除的文件**（自己这一轮动过的那些），**不是** `git status` 里的全部内容。
- 逐个对照当前状态：已经没有改动的路径要去掉（本会话前面提交过、或被回退过的会落在这里）。
- 工作区里**不属于本次会话**的改动：**不要提交**，也不用在预览里铺开列给用户看（默认只报一处数「另有 N 处改动不属于本次会话」）。用户要明细时再加 `--show-excluded`。
- 没有可提交的改动时：说清楚然后停下，**不要造空提交**（不要 `--allow-empty`）。
- 只接受具体文件路径；传目录会被脚本拒绝（目录会把别人改过的文件一起卷进来）。

## 2. message 格式

格式固定为 `type: 中文简述`（半角冒号 + 一个空格）。

| type | 用在 |
| --- | --- |
| `feat` | 新功能 / 新能力 |
| `fix` | 修 bug、修错误行为 |
| `docs` | 只改文档、注释 |
| `style` | 只改格式、命名、排版，不改行为 |
| `refactor` | 重构，行为不变 |
| `perf` | 性能 |
| `test` | 测试脚本 |
| `build` | 构建、依赖、资源复制 |
| `chore` | 杂项维护 |
| `revert` | 回退某次提交 |

- **不写 scope**：写 `fix: 时间轴不重建`，不写 `fix(player): 时间轴不重建`。
- **只写一行**，不写正文 —— 所有信息压进那一行简述里（脚本会拒绝多行 message）。
- 一行里说清**改了什么、影响哪一块**，不超过 72 字符，结尾不加句号。
- **禁止没有信息量的简述**：`更新` / `修改` / `调整` / `改动` / `优化` / `完善` / `杂项` / `其他` / `一些改动` / `update` / `updates` / `fix` / `fixes` / `changes` / `misc` / `wip` / `stuff`（脚本按精确匹配拦，`fix: 修复导出按钮` 不受影响）。
- 例子：`fix: 删除小节后时间轴不重建`、`docs: 补 pt 与 px 混用的判定`。
- 纯文档提交可以把 `[skip ci]` 缀在同一行末尾（见 `deployment.md`）：**默认不加**，用户要求才加。

## 3. 流程 A：`commit xxxxx` —— 直接提交

用户把 message 打给你了，**类型前缀由你判定**，判完直接提交，不用再找他确认：

```
npm run commit -- --write --message "<type>: xxxxx" -- <文件…>
```

- 用户给的文字**已经带**合法 `type: ` 前缀就照用；没带就按第 2 节的表自己挑一个。
- 用户给的文字如果太长 / 太空泛（脚本会拒绝），按第 2 节改写得更短更具体再提交 —— 这是用户自己给的 message，不用再问一遍。
- 提交后把 **commit 首行 + 实际进提交的文件列表**回给用户。

## 3.5 流程 B：只说了 `commit` —— 先给用户确认

**预览**（read-only，不写任何东西）：

```
npm run commit -- --preview --message "fix: 删除小节后时间轴不重建" -- <文件…>
```

把打印出来的整段**原样给用户看**（本次提交的文件清单与改动量 / message / 指纹），然后**停下等他确认**。用户要确认的就是这两样东西。

- 用 `--message "…"` 传那一行 message 就行（**message 里不要有换行**：带换行的参数在 PowerShell → npm → cmd 这一路会被拆坏，脚本也会拒绝多行 message）。
- 用户改了 message → 用新 message 重新预览一遍，不要自己改完直接提交。
- 用户没说「确认」之前不要提交。

**提交**（用户确认后）：

```
npm run commit -- --write --message "fix: 删除小节后时间轴不重建" --expect <预览打印的指纹> -- <文件…>
```

- 这条路上 `--expect` **必须**给。指纹对不上 = 预览之后文件被动过（典型是另一个 agent 改了同一个文件）→ 脚本拒绝并重新打印一份预览：**重新给用户看**，不要绕过指纹检查。
- **不 push**。要 push 另外问用户。

其他参数：`--show-excluded` 逐条列出不属于本次会话的改动；`--diff-lines <n>` 在预览里附 diff（默认 `0` = 不附，用户要看得单独跑 `git diff`）。

## 4. 不要做的事

- **不用 `git add -A` / `git add .` / `git commit -a`**，尤其**不用不带路径的 `git commit`**：不带路径的提交收的是**共享 index**，会把别人已暂存的内容一起提交走。
- **不自己拼 git 命令代替脚本**。脚本固定用 `git add -- <路径>` + `git commit --only -- <路径>`（只动清单里的路径），并处理了这些坑：未跟踪文件必须先 `git add` 否则 `--only` 的 pathspec 匹配不到；重命名要两侧一起提交；删除 / 改名后的旧路径不在工作区、不能对它跑 `git add`；`.git/index.lock` 冲突要重试。
- 不跑 `--amend` / `rebase` / `reset` / `restore` / `checkout --` / `stash` / `clean` / `push --force`。
- 不提交 `artifacts/`、`dist/`、`src/i18n/locales.generated.js`、`public/pdfjs/`（都在 `.gitignore` 里，不要 `-f` 强加）。

## 5. 并发时会发生什么

- **两个 agent 同时提交**：不带路径的 `git commit` 提交的是共享 index，谁先跑谁就把对方已暂存的改动一起收走 —— 所以清单和 `--only` 是硬要求。清单里的路径之外的东西一律不动，包括对方已暂存的内容。
- **预览到确认之间内容变了**：指纹对不上，脚本拒绝。这是唯一能挡住「把别人的改动写进我的 message」的机制，所以 `--expect` 不能省。
- **`.git/index.lock` 被占用**：脚本短暂重试；重试仍失败就报错退出 —— 报错就是报错，不要并发硬闯、不要绕开脚本。
- **重命名**：只列一侧会留下半个重命名（新路径提交进去了，旧路径的删除悬在工作区），脚本会拒绝并要求两个路径都列上。`git status` 对**未暂存**的重命名配不成对、认不出来，这种情况脚本放行但会在预览里打出「重命名只列了一半」的提醒 —— 看到提醒要跟用户确认，不要当成噪音划过去。
